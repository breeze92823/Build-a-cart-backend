# Build a Cart — BACKEND (game server)

Frontend (3D client) lives at `../Build-a-cart` (its `src/net.js` talks to this server). Colyseus + Mongo, ported from the Bowling Roll backend (some systems below are carried over and not used by this client yet).

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { token, username, pfp, avatar?, outfit?, pose?, loadout? })`; off production `devId` / legacy `userId` also identify, see Identity). The room holds `ROOM_MAX_CLIENTS` = 5 players (one per base; a sixth join spills into a fresh room). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- This server's Mongo doc is the signed-in player's save. A guest's (or a serverless session's) progress lasts the page only.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ token?, devId?, username, pfp, avatar?, outfit? }` after a sign-in/out mid-session: re-verified; with none of `token`/`devId`/`userId` present only name, picture and look change, `token: null` = signed out = guest), `questsRefresh`, `rerollQuests` (see Quests), `race` (`{ racing, distance }`; distance clamped 0..`DISTANCE_MAX`, 0 when not racing). Server -> client (private): `progress` (the saved doc, sanitized, + `serverTime`), `noProgress` (`{ serverTime }`: new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), then `quests`, `spins`, `daily`, `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp` (Bloxity profile picture URL, http(s) only, max `PFP_MAX_LEN`, "" = none), `racing`, `distance` (`test/Roster.test.ts`).
- Saved progress shape (`PlayerDoc` in `src/db.ts`, the client's `saveProgress` payload; `progress` gives the same back, sanitized). Times marked (s) are epoch SECONDS, client clock:
  - `cash`, `totalEarned`: numbers 0..`CURRENCY_MAX`.
  - `owned` `{ gearId: count }` (ids match `ID_PATTERN`, at most `OWNED_MAX` keys, counts whole 0..`OWNED_COUNT_MAX`, 0s dropped); `equipped` `{ engine, fuel, wheels, booster }` (only those keys, only well-formed ids); `discovered[]` gear ids (a `{ id: true }` map is accepted too).
  - `wagons` 0..100, `goldenCarts` 0..1e6, `rebirths` 0..`REBIRTHS_MAX` (ints); `passes[]` pass ids (all bought with Cash).
  - `stats` `{ rides, best, gearBought, wagonsBought, spins, boosts, jumps, totalDistance, playtime, upgradesBought, invites }` finite >= 0, bounded, unknown keys dropped. Derived top-level `best` (= `stats.best`, saved with `$max` so it never drops) and `playtime` (= `stats.playtime`) for the leaderboards.
  - `upgrades` `{ power, tank, aero, dist, mult, cur }` ints 0..1000; `topRuns[]` (max 8) `{ d, cash }` >= 0.
  - `lastGift`, `spinAt` (the client's lucky wheel), `cashBoostUntil`: (s) >= 0, at most now + 1 year; `fuelNextRun` boolean.
  - `restock` `{ period (int, -1 = none), nonce 0..1e9, bought { id: int } }`; `loadouts[]` (max 10) `null` or `{ engine, fuel, wheels, booster }` (position = slot); `slotsOpen[]` unique ints 0..9.
  - `stars` 0..1e9, `questLevel` 0..1e6, `dice` 0..1e6 (ints).
  - `quests` `{ daily: { period, progress: { stat: n >= 0 } (stat keys match `ID_PATTERN`, at most 16), done: [quest ids] }, weekly: same }`: the client's progress on the server's pick.
  - `lastSeen` (ms; also stamped by the server when a player really leaves).
  - Server-owned, never accepted from `saveProgress`: `srvSpins`/`srvSpinAt`, `dailyDay`/`dailyLast`/`dailyClaimed`, `questDaily`/`questWeekly`.
- Quests (`src/quests.ts`, `test/Quests.test.ts`, constants `QUEST_POOLS` / `QUESTS_PER_PERIOD` = 5): the SERVER picks which quests are on, on its UTC clock. Pools must match the client's `QUESTS.daily/weekly.pool` ids (daily `warmup, steady, champion, collector, walker, rider, hopper, shopper, mechanic, booster, lucky`; weekly `warrior, community, grinder, weeklychamp, explorer, earner, gapmaster, regular`). Periods: `dailyPeriod = floor(now / 86_400_000)`; weeks start Monday 00:00 UTC, `weeklyPeriod = floor((floor(now / 86_400_000) + 3) / 7)`; `endsAt` daily `(period + 1) * 86_400_000`, weekly `((period + 1) * 7 - 3) * 86_400_000`. The pick is a mulberry32-seeded (period, rerolls, per-kind salt) choice of 5 distinct pool ids. Per session `{ daily, weekly: { period, ids, rerolls } }` in `quests`, read from doc `questDaily`/`questWeekly` (server-written, `saveQuests`), rolled on load (new period -> new pick, rerolls 0). After `progress`/`noProgress` the client gets `quests` `{ daily: { period, ids, endsAt }, weekly: { period, ids, endsAt }, serverTime }`. `questsRefresh` (countdown hit zero): rolls if the period changed, answers `quests`. `rerollQuests` `{ kind: "daily" | "weekly", keep: [finished ids] }`: kept ids (only those in the current pick) stay in place, every other slot gets a pool id not currently on (pool short -> any pool id not kept), distinct; rerolls++, stored, answers `questsResult` `{ ok: true, kind, period, ids, endsAt }` or `{ ok: false, kind, reason: "loading" | "kind" }`. The client charges the Cash itself and tracks progress/rewards/stars in its saved `quests`. Guests / no-DB sessions keep the pick in memory for the connection.
- Spin wheel (`src/spin.ts`, constants `SPIN_*`; not used by this client yet, its lucky wheel is the client-saved `spinAt`): server-authoritative. Each session's `{ spins, nextAt }` lives in `spinStates` (read from the doc's `srvSpins`/`srvSpinAt`, prefixed so they never collide with the client's `spinAt`; a new player gets `SPIN_START`), one free spin accrues every `SPIN_EVERY_MS` up to `SPIN_CAP`. After the load the server sends `spins` { spins, nextAt, serverTime }; `spin` answers `spinResult` { ok, id, spins, nextAt, serverTime } (or { ok: false, reason: "loading" | "none" }) and writes `srvSpins`/`srvSpinAt`.
- Daily Reward (`src/daily.ts`, `DAILY_DAYS`; not used by this client yet): server-authoritative on the UTC clock. Doc fields `dailyDay`, `dailyLast`, `dailyClaimed[]`, written only by the server (`saveDaily`). On load today unlocks (`rollDaily`) and the client gets `daily` { unlocked, claimed, nextAt, serverTime }. `claimDaily` { day } answers `dailyResult` { ok, day, reason?: "loading" | "locked" | "save", ...view }; `dailyRefresh` re-rolls after midnight and answers `daily` (`test/Daily.test.ts`).
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`rebirths`, `totalEarned`, `best` = best ride distance, `playtime`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS`. `connectDb` creates a descending index per stat. The test fake supports just that find/countDocuments shape.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): what the other 4 players draw. Everything is relayed through the roster as sent, only bounded (client-authoritative, cosmetic). `PlayerState` fields: `username`, `signedIn`, `pfp`, `racing`, `distance`, `uid` (verified Bloxity id, "" = guest; public so the client can match chat-bubble `userId`s), `x`/`y`/`z` (feet, world coordinates as the sender sees them), `yaw`, `speed`, `grounded`, `avatar` (look JSON), `outfit` (Bloxity outfit key, <= `OUTFIT_MAX_LEN`; the platform-verified key from the token wins over the client's), gear ids `engine`/`fuel`/`wheels`/`booster` (`ID_PATTERN` or ""), `wagons` / `golden` (0..100), the ride `ride` ("foot" | "riding" | "crashed" | "ending") / `crash` (kind while crashed), `s` (m along the track), `cy`, `pitch`, `roll`, `lx` (lane offset), `v`, `throttle`, `braking`, `boosting`, `air`, `fuelOk`, `tip` (bounds in `CART_BOUNDS`), `emote` (Bloxity emote id, `EMOTE_PATTERN`) and `emoteSeq` (uint16, +1 on every accepted `emote` message so a repeat restarts it). Messages: `pose` { x, y, z, yaw, speed, grounded } (~10/s), `cart` { ride, crash, s, cy, pitch, roll, lx, v, throttle, braking, boosting, air, fuelOk, tip } (~15/s while riding; every field optional, a malformed one is ignored), `loadout` { engine, fuel, wheels, booster, wagons, golden }, `setAvatar` { avatar, outfit } (or the join options), `emote` { id } ("" stops). Chat bubbles / emotes are drawn by the client from Bloxity's own chat and `play_emote` events.
- Identity (`src/auth.ts`, `test/Bloxity.test.ts`): the client sends its Bloxity game token (`token`) on join / `identify`; the server verifies it with `POST {BLOXITY_API_URL}/v1/auth/game-token/verify` (`Authorization: Bearer`, body `{ gameSlug }`) and uses ONLY the returned `user._id` (plus `displayName`/`username` and `outfitKey` when present) as the account. Answers are cached 60 s (a hash of the token is the key). In production (`NODE_ENV=production`) no token / a refused one / an outage = a guest: a client-sent id is never trusted. Off production a `devId` (`dev-...`, the client's VITE_DEV_MODE id) or legacy `userId` (anything not `guest-...`) identifies, so local tabs and the tests work without Bloxity. `onJoin` waits for the verification (6 s timeout) before loading the save.
- Rewarded ads (`src/adReward.ts`): `adReward` { rewardToken } -> reply `adReward` { ok } or { ok: false, reason: "cooldown" | "invalid" }. The token is checked once with `POST {BLOXITY_API_URL}/v1/ads/reward/verify` (`valid: true` only; an outage is a no); a session may redeem one every `AD_COOLDOWN_MS` (60 s; a failed try starts no cooldown). The client grants the reward only on `ok`.
- Bloxity leaderboards (`src/platformBoards.ts`): `PLATFORM_BOARDS` (`best` distance, `earned`, `rebirths`, `playtime` in minutes) must match the client's `LEADERBOARDS`. After each successful `saveProgress` of a Bloxity-verified (not `dev-`/`guest-`) account its latest scores are queued, and every `PLATFORM_BOARD_EVERY_MS` (30 s) up to `PLATFORM_BOARD_BATCH` (200) scores are posted to `{BLOXITY_API_URL}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report` (`Bearer BLOXITY_REPORT_TOKEN`, board declarations ride along; only `legion_` ids rank). No-op without `BLOXITY_REPORT_TOKEN`. (The in-game `leaderboard` message of `src/leaderboard.ts` is separate.)
- Room directory (`src/legion-room-reporter.ts`): every 2 s this pod's rooms are POSTed to `{MATCHMAKER_REPORT_URL}/{gameId}/rooms` so Open Rooms / join-by-id work across pods; no-op without `MATCHMAKER_REPORT_URL` + `BLOXITY_REPORT_TOKEN`. `onCreate({ private: true })` makes the room private (CrazyGames "Play with friends").
- SIGTERM drain (`src/drain.ts`, `src/index.ts`, `test/Drain.test.ts`): Colyseus' own immediate graceful shutdown is off (`gracefullyShutdown: false` in `app.config.ts`). On SIGTERM every room is locked (the matchmaker sends new players to the new pod), the riders here keep playing until they leave or `DRAIN_MAX_MS` (9 min; Legion waits 10) passes, the last scores are reported, then `server.gracefullyShutdown(true)`. SIGINT (Ctrl-C) shuts down at once.
- Env (all optional locally, see `.env.example`): `BLOXITY_API_URL`, `BLOXITY_GAME_ID`, `BLOXITY_REPORT_TOKEN`, `MATCHMAKER_REPORT_URL`, `POD_NAME`, `JWT_SECRET`, `MONGODB_URI`, `CLIENT_ORIGIN`, `PORT`, `NODE_ENV`.
- `src/constants.ts` bounds must cover the client's `src/config.js` (catalog/quest/pass ids match `ID_PATTERN`). Everything in the game is bought with Cash (never premium currency). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the matchmaker sizes pods). The game slug is the repo/folder name lowercased without `-backend` (`build-a-cart`); repo var/secret `LEGION_GAME_ID` is only an optional override. Needs secret `LEGION_DEPLOY_TOKEN`.
